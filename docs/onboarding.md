# تحویل مشتری تازه

این فهرست کار را می‌شود از اول تا آخر دنبال کرد، **بدون دست‌زدن به کد**. با همین مسیر
یک مشتری ساختگی (`trial`، روی یک دیتابیس تازه‌ی محلی با نام‌های دیگر) از صفر تا
«همه ✅ و ۱۲ از ۱۲ جواب درست» رسید و `git status` فقط پوشه‌ی `customers/trial/` را
نشان داد. اگر جایی گیر کردید یا چیزی از قلم افتاده بود، همین سند را اصلاح کنید و در
`PLAN.md` (لاگ تصمیم‌ها) ثبت کنید.

> **اصل:** هر مشتری یک پروسه (کانتینر) جدا دارد با `.env` و `RASAM_CUSTOMER` خودش
> (تصمیم ۸۰). جداسازی کامل است: هیچ باگی نمی‌تواند داده‌ی یک مشتری را به دیگری نشان دهد.

## ۰. از مشتری بپرسید

۱. **نوع دیتابیس** چیست؟ فعلاً فقط MongoDB آماده است. نوع دیگر یعنی اول
   [`docs/adding-a-database.md`](adding-a-database.md).
۲. یک **کاربر فقط-خواندنی** برایمان می‌سازد؟ (مرحله‌ی ۱.) *هرگز* اتصال مدیر نمی‌خواهیم.
۳. سرور ما به دیتابیسش **شبکه** دارد؟
۴. کدام کالکشن‌ها یا جدول‌ها برای پاسخ‌دادن لازم‌اند؟ **جدول‌های حساس** (کاربران،
   صورت‌حساب، لاگ) را کنار بگذارید: فقط منابعی که انتخاب می‌کنید توصیف می‌شوند و
   خوانده می‌شوند، ولی هرچه کمتر، بهتر.
۵. **ده سوال واقعی** که کاربرانش می‌پرسند (به همان زبانی که می‌پرسند).
۶. چه واژه‌هایی را به چه معنایی به کار می‌برند؟ چه تله‌هایی در داده هست (فیلدی که
   همیشه خالی است، عددی که علامتش درست ذخیره نشده، دو فیلد شبیه هم)؟

## ۱. کاربر فقط-خواندنی (در محیط مشتری)

برای MongoDB، مشتری (یا ما با اتصال او) این را اجرا می‌کند:

```js
use <نام_دیتابیس>
db.createUser({
  user: "rasam_ro",
  pwd: "<رمز قوی>",
  roles: [{ role: "read", db: "<نام_دیتابیس>" }]
})
```

نقش `read` همان چیزی است که بررسی تحویل (`check`) می‌پذیرد؛ هر نقش دیگری که اکشن
غیرخواندنی داشته باشد قرمز می‌شود. مونگوی مشتری باید **auth روشن** باشد، وگرنه نقش‌ها
اعمال نمی‌شوند و «فقط-خواندنی» معنایی ندارد.

## ۲. رشته‌ی اتصال در `.env` سرور

رشته‌ی اتصال کاربر بالا را با یک نام دلخواه در `.env` همان پروسه بگذارید، با پیشوند
`RASAM_`:

```
RASAM_ACME_DB_URI=mongodb://rasam_ro:<رمز>@<میزبان>:27017/<نام_دیتابیس>
```

**این رشته هرگز در `customers/` یا مخزن نمی‌نشیند.** ابزار تحویل فقط *نام* متغیر را
می‌پرسد، و بارگذار پروفایل هر مقدار شبیه رشته‌ی اتصال یا رمز را رد می‌کند.

> اگر دستورها را از یک ترمینال می‌زنید و متغیر را با `export` گذاشته‌اید، همان ترمینال
> باید هر دستور بعدی را هم اجرا کند؛ در `.env` این مشکل نیست.

## ۳. ساختن پوشه‌ی مشتری

```bash
python onboard.py new
```

می‌پرسد: نام مشتری · نوع دیتابیس · **نام** متغیر اتصال · نام دیتابیس، سپس منابع
دیتابیس را فهرست می‌کند و شما با شماره انتخاب می‌کنید (پیش‌فرض هیچ‌کدام). منبعی که
نامش حساس به نظر برسد (`users`، `billing`، `secrets_log`، …) یک بار دیگر صریحاً تایید
می‌خواهد. **شماره‌ها را دوباره بخوانید** — در تمرین تحویل، `1,3` به‌جای `1,2` یک جدول
حساس را مجاز کرد. خروجی: `customers/<نام>/` با پنج فایل (`profile.yaml`،
`documentation.md`، `examples.yaml`، `field_notes.yaml`، `golden_questions.yaml`).

## ۴. تکمیل دانش دامنه — با خود مشتری

ابزار این را **حدس نمی‌زند**. هر جای خالی با `TODO(onboarding)` علامت خورده است.

- **`documentation.md`** (به انگلیسی، چون مستقیم وارد پرامپت مدل می‌شود): هر منبع چه
  چیزی نگه می‌دارد و کاربر فارسی‌زبان به آن چه می‌گوید؛ جدول «کاربر می‌گوید ← یعنی»؛
  و بخش تله‌های داده با *راه‌حل دقیق* هر تله.
- **`field_notes.yaml`**: یک جمله‌ی کوتاه برای فیلدهایی که مدل درباره‌شان اشتباه می‌کند.
- **`examples.yaml`**: چند نمونه‌ی «سوال ← کوئری درست»، هرکدام با `why`. هر نمونه باید
  از گارد رد شود (`check` این را می‌سنجد).

> **درسی از تمرین تحویل:** هر تله‌ی داده را با **دامنه‌ی اجرایش** بنویسید، نه فقط با
> راه‌حلش. «ولتاژ صفر یعنی استرینگ قطع است» باعث شد مدل در *میانگین* هم صفرها را کنار
> بگذارد و عدد غلط بدهد (۶۶۶ به‌جای ۴۶۵)؛ بعد از نوشتن «فقط برای کمترین مقدار، و
> میانگین و بیشترین و شمارش با همه‌ی داکیومنت‌ها» درست شد. یک سوال طلایی برای هر تله،
> همین‌جور خطاها را زود نشان می‌دهد.

## ۵. سوالات طلایی

در `golden_questions.yaml` دست‌کم **۱۰ سوال** بنویسید و جوابشان را **از خودِ دیتابیس**
بگیرید (با `mongosh` یا هر ابزار فقط-خواندنی)، نه از حدس. سه شکل پذیرفته می‌شود: جواب
عددی (`value`)، نتیجه‌ی خالی (`empty`)، و «این داده نیست» (`message`) — از هر سه
دست‌کم یکی داشته باشید. مثال‌ها در بالای فایل است.

## ۶. روشن‌کردن مشتری و پرسیدن اولین سوال

در `.env` همان پروسه:

```
RASAM_CUSTOMER=<نام>
```

```bash
python ask.py "یک سوال ساده"
```

## ۷. بررسی آمادگی

```bash
python onboard.py check <نام>
```

باید **همه ✅** شود (کد خروج ۰). هر ❌ دلیلش را به فارسی می‌گوید. با مدل تماس
نمی‌گیرد، پس هر چندبار لازم باشد اجرایش کنید.

## ۸. سنجه‌ی کیفیت (هزینه دارد — جداست)

```bash
python scripts/evaluate.py
```

درصد سوالات طلایی که درست جواب می‌گیرند. **نمره‌ی قابل‌قبول:** پیشنهاد اولیه ≥ ۸۰٪، و
هر جواب غلط باید بازبینی شود: اغلب یک سطر در `documentation.md` یا یک نمونه‌ی
تازه در `examples.yaml` حلش می‌کند. این عدد با اولین مشتری واقعی محک می‌خورد.
سوالی که به‌خاطر خطای سرویس مدل سنجیده نشد، «غلط» شمرده نمی‌شود.
